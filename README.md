ImeAudio 是一款高性能、AI 驱动的实时语音转录与文本润色工具。旨在为用户提供无缝的工作流体验，通过结合顶尖的本地与云端语音识别引擎，将您的语音瞬间转化为精准、优雅的文字。

## 🌟 核心功能

### 🎙️ 智能语音转录
* **多引擎支持：** 支持本地 **Sherpa** 引擎，或使用 **Gemini**、**Groq**、**Gladia** 等高性能云端引擎。
* **智能语音检测 (VAD)：** 自动识别语音片段，实现高效、精准的录音与处理。
* **实时频谱可视化：** 基于 FFT 的精美频谱与波形动画，实时反馈音频状态。

### ✨ AI 文本精炼
* **智能润色：** 利用大语言模型 (LLM) 自动修复语法、调整语气或重新编排文本。
* **高度自定义：** 支持自定义 Prompt、专业 AI 词库以及文本替换规则。
* **术语管理：** 内置 `Terms Library`（术语库），确保专业词汇转录的准确性。

### 🛠️ 无缝工作流
* **全局热键：** 支持通过快捷键随时随地触发转录，不中断现有操作。
* **现代化 UI/UX：** 基于 Qt/QML 构建，拥有类似 macOS 的精致界面、平滑动画与现代审美。
* **后台运行：** 轻量级系统托盘集成，实现静默高效工作。
* **自动更新：** 内置自动更新机制，始终保持功能最新。

## 🛠 技术栈
* **框架:** Qt 6 (C++/QML)
* **音频引擎:** miniaudio / QAudioSource
* **数字信号处理 (DSP):** kiss_fft
* **AI 引擎:** Sherpa (本地), Gemini, Groq, OpenAI


## 🗺️ 未来方向与计划 (Roadmap)

> 原则：先把核心转录+润色链路做到极致稳定和精准，再考虑横向扩展。宁可少而精，不做无法长期维护的功能堆砌。

### 🎯 第一优先级：核心体验打磨（近期）

- **转录准确率与延迟的量化基准**
  建立标准测试集，对本地 Sherpa 与各云端引擎做横向评测，用数据说话，而不是凭感觉调参。作为后续所有引擎优化的判断依据。
- **VAD 断句准确性优化**
  当前语音检测在长句停顿、快语速、气口不明显的场景下容易误切/漏切，优先解决"一句话被切成两段"或"该停的地方没停"的问题，这类细节直接影响转录可用性。
- **术语库匹配的健壮性**
  修复现有双语术语匹配逻辑中的边界情况，确保术语替换在各种输入下不崩溃、不误替换。
- 多语言 UI 全覆盖 —— 先做好中英文的极致体验，其他语言按实际用户地域分布决定优先级。

### 🧠 第二优先级：AI 能力深化（中期）

- **本地 LLM 润色支持（Ollama / llama.cpp）**
  优先支持 1-2 个主流本地模型（如 Qwen2.5、Llama 3 系列的量化版本），先做通、做稳一条路径，而不是一开始就想兼容所有本地模型生态。
- **流式润色（渐进式展示）**
  在语音输入过程中逐步展示润色结果，重点是解决"用户等待感"，而非追求实时性能上的极致——先做到"边说边看到修正"的体验闭环即可。
- **润色 Prompt 模板的场景化预设**
  与其做"通用可自定义"，不如先内置几套针对具体场景调好的模板（如会议纪要、邮件、代码注释口述），降低新用户配置门槛，验证哪些场景真正高频后再决定要不要开放模板市场。

### 🔌 第三优先级：引擎与平台横向扩展（视资源投入而定）

	- **新增云端 ASR/LLM 接入**：按用户实际反馈的高频需求排序（例如先看 Issues 里哪个引擎被点名最多），而非一次性铺开所有候选。
- **macOS / Linux 正式版**：优先做好其中一个平台的完整原生体验（菜单栏集成、权限模型、打包发布流程），验证跨平台维护成本后再推进第二个平台，避免两边都是半成品。

### 🛡️ 质量与工程基建（贯穿始终）

- **自动化测试�covers关键路径**：录音→VAD→转录→润色→输出 这条主链路建立自动化回归测试，防止新功能引入回归问题（例如上次遇到的 tuple 解包不匹配这类问题，本可以被单元测试提前拦截）。
- **崩溃/异常上报机制**：轻量级的本地异常日志收集（用户可选择是否上传），帮助快速定位真实用户环境下的问题，而不是只能靠用户手动反馈日志。
- **资源占用基线监控**：为 CPU/内存占用设定明确的基线指标（例如"待机状态下不超过 XX MB"），作为后续功能开发时是否引入性能回归的硬性检查项。


> 💡 以上计划会根据社区反馈和实际开发进度动态调整，欢迎在 Issues 中提出你的想法！

以下是 sherpa-onnx 支持的**非流式（离线/offline）ASR 模型**清单，讲解了每种的特点和典型场景：

| 模型类别 | 通俗解释 | 核心特点 | 适合场景 |
|---|---|---|---|
| **Transducer（离线版）** | 基于 Zipformer/Conformer 架构的"一次性"转写器 | 精度和速度平衡得很好，是社区最常用的基础款 | 通用语音转文字，尤其是需要自己训练/微调模型的场景 |
| **Paraformer** | 阿里 FunASR 出品的中文识别利器 | 非自回归解码，速度快，中文识别效果拔尖 | 中文语音转写、会议记录、字幕生成 |
| **NemoCTC** | 英伟达 NeMo 框架的 CTC 模型 | 结构简单、推理快，模型体积通常较小 | 资源受限设备上做英文/多语种识别 |
| **Whisper** | OpenAI 开源的明星模型 | 多语言能力强、抗噪声/口音能力好，但比同类模型慢一些 | 多语言混杂音频、口音较重或环境嘈杂的录音转写 |
| **Tdnn** | 老牌轻量级模型（TDNN 结构） | 体积极小，几乎不占资源 | 简单的关键词/命令词识别（比如经典的 yesno 示例），嵌入式场景 |
| **SenseVoice** | 阿里出的多语言"全能选手" | 除了转文字，还能识别情感、语种，甚至区分说话内容/音乐/环境音 | 需要附加信息（语种检测、情感标注）的多语言转写任务 |
| **Moonshine** | 专攻英文的轻量模型 | 针对短句英文优化，速度快、延迟低 | 英文语音助手、实时命令识别（虽然是离线模型但延迟很低） |
| **FireRedAsr（含 CTC 版）** | 小红书出品的中文识别模型 | 编码器-解码器结构，中文效果好，也有轻量的 CTC 版本可选 | 中文语音转写，对准确率要求较高但也要兼顾速度时选 CTC 版 |
| **FunAsrNano** | 基于 LLM 的轻量 FunASR 版本 | 结合大模型能力，理解上下文更好 | 需要更强语义理解的中文转写场景 |
| **Dolphin** | 单模型架构的识别器 | 结构精简，一个模型搞定端到端识别 | 需要部署简单、依赖少的场景 |
| **ZipformerCtc** | Zipformer 架构的 CTC 版本 | 比 Transducer 版本更轻量，推理更快 | 对速度要求高于精度的场景 |
| **Canary** | 英伟达 NeMo 的编码器-解码器模型 | 支持指定语言进行解码，多语言支持好 | 明确知道音频语种、需要高精度多语言转写的场景 |
| **WenetCtc** | WeNet 框架的 CTC 模型 | 工业界广泛验证过的方案，稳定可靠 | 生产环境部署，尤其中文场景 |
| **Omnilingual** | "全语言"识别模型，覆盖 1600+ 种语言 | 语种覆盖极广，包括很多小语种 | 不确定音频是什么语言、或需要支持冷门语种时 |
| **MedAsr** | 医疗领域专用识别模型 | 针对医学术语、病历口述等场景做过优化 | 医院病历口述转写、医疗问诊记录 |
| **Qwen3ASR** | 阿里千问系列的多模态识别模型 | 单模型支持数十种语言（中、英、粤语、阿拉伯语等），理解能力强 | 多语言、跨语种混说的复杂场景，比如国际会议、多语种客服 |
| **CohereTranscribe** | Cohere 提供的转写模型 | 定位企业级转写场景 | 需要企业级稳定性和多语言支持的转写任务 |

**几个选型建议（大白话版）：**
- **只做中文、追求速度** → 优先试 Paraformer 或 WenetCtc
- **多语言混杂/口音重** → Whisper 或 Qwen3ASR
- **嵌入式/资源极度受限** → Tdnn、Moonshine、ZipformerCtc（体积小）
- **冷门小语种** → Omnilingual（1600+ 种语言覆盖，几乎是万能兜底选项）
- **医疗行业专用** → MedAsr
- **需要额外信息（情感/语种/环境音）** → SenseVoice
